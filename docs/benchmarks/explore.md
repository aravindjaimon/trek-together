## Method

2000 public routes are seeded across a ~1.8° box around Shenandoah
(38.55, -78.29); the query asks for routes within 25 km.
Because `$geoNear` mandates a 2dsphere index, the **on/off** contrast is measured with the equivalent
`$geoWithin`/`$centerSphere` filter (runs either way), via `explain(executionStats)`. The production
`$geoNear` path is then validated with the index present.

## Results

| Scenario | Index used | Docs examined | p50 latency |
|---|---|---|---|
| 2dsphere **ON** | `path_2dsphere` | 204 | 2.09 ms |
| 2dsphere **OFF** | `routes_isPublic_idx` | 2000 | 3.54 ms |

- Both return **139** matching routes. With the geo index Mongo seeks via
  `path_2dsphere` and examines only ~204 docs; without it the planner falls
  back to the `routes_isPublic_idx` index and post-filters the geometry over all
  **2000** public docs.
- **~1.7× faster** with the geo index at this collection size — and the docs-examined
  gap (204 vs 2000) grows linearly as routes accumulate.
- Production `routes.explore` uses `$geoNear` (winning stage `GEO_NEAR_2DSPHERE`), which **requires**
  the 2dsphere index created by `packages/db/src/setup-indexes.ts`.

## Notes

- Latencies are tiny at 2000 docs; the **docs-examined** column is the durable signal — index
  turns an O(n) scan into an index seek.
